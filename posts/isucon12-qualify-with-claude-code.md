# Claude Code に ISUCON12 予選を回させたら 1,034,789点だった

> この記事の文章は、作業記録をもとにほとんどを AI（Claude Code）が書いています。

[private-isu](/blog/private-isu-with-claude-code/)、[ISUCON14](/blog/isucon14-with-claude-code/)、[ISUCON13](/blog/isucon13-with-claude-code/) に続く記事です。今回は **ISUCON12 予選**（isuports、マルチテナントの大会スコア管理 SaaS）を、環境構築から計測・改善・デプロイ・記録まで Claude Code に回させました。

これまでと違う点が2つあります。

- **過去3回の練習から知見を集めたリポジトリを、最初に読ませた。** 進め方（開始30分の手順、`make bench` が何をすべきか、やってはいけないこと）はそこに書いてあり、Claude Code はそれに沿って今回用の CLAUDE.md・計測スクリプト・skill を自分で作っています
- **放置していない。** 判断が必要なところで Claude Code のほうから質問が来て、私が答える形で進みました

最初のプロンプトはこれだけです。

> isucon-tools の構成を参考にしつつ、isucon12予選を解いていきたい。環境構築は isuenv で。改善作業を回し、とにかく最高点を目指してください。TTL は6時間で設定して、回していきましょう。

コードは1行も書いていません。モデルは **Claude Opus 5.5** です。

- リポジトリ: [kyosu-1/isucon12-qualify-2026](https://github.com/kyosu-1/isucon12-qualify-2026)
- 環境構築に使った自作CLI: [kyosu-1/isuenv](https://github.com/kyosu-1/isuenv)

## 結果

**2,033 → 約103万（安定）、最高 1,197,784。** 環境を作ってから最終計測まで3時間15分、記録に残した計測は51回、その時点のコミットは72件です。

タイトルの数字は最終構成の最高値です。全体の最高点である 1,197,784 を書かなかったのは、その構成が安定しないからです。

| 構成 | スコア | 安定性 |
|---|---:|---|
| 最終構成（テナントを3台に均等） | 1,010,919 〜 1,034,789 | 6回計測して FAIL なし、エラーは最大2件。3台を再起動した後も 1,034,663 |
| 最高点の構成（1号機を中継専任に） | **1,197,784** | 5回連続で測ると 923,295 / FAIL / FAIL / 1,168,611 / 1,191,223 |

最高点の構成は、減点前のスコアなら毎回約120万で揃っています。それが FAIL になったり119万になったりするのは、サーバーではなく練習環境側の事情でした（後述）。最終状態は安定するほうにしてあります。

| 時刻 | スコア | 変更 |
|---|---:|---|
| 16:11 | 2,033 | ベースライン（Go / 無改善） |
| 16:24 | 256,633 | データをメモリに持つ形に一括で書き換え（後述） |
| 16:29 | 259,537 | 3台構成。**変わらず。ベンチマーカーの CPU が 95%** |
| | | **← 17:25 ベンチマーカーを c5.large → c5.4xlarge に変更（確認のうえ）** |
| 17:36 | 828,537 | TLS を3台のアプリで直接終端（nginx は中継だけ） |
| 17:43 | 875,796 | 多く呼ばれる3つの API の JSON を手書き |
| 17:47 | 946,636 | TLS ハンドシェイクの RSA 署名を OpenSSL に |
| 17:51 | 975,983 | 参加者情報のレスポンスをキャッシュ |
| 18:18 | 1,105,386 | HTTP/2 をやめて HTTP/1.1 に |
| 18:52 | **1,197,784** | 1号機を中継 + MySQL + 管理 API の専任に（不安定） |
| 19:12 | 1,034,789 | テナントを3台均等に戻す（最終構成） |

### 本番のスコアとは比べられない

本番の数字と直接は比べられません。本番は8時間の制限の中で、運営の環境からベンチマーカーが走っています。公式の解説には、Ruby 実装・SQLite のまま1台構成で「予選突破相当のスコア(24,000点)」を確認した、とあります。こちらは公開されているベンチマーカーを同じ VPC のマシンで回していて、しかも途中からそのマシンを 16 vCPU にしています。「この環境で、同じ物差しで測って何倍になったか」の数字です。

## 最初の25万点は、計測で見つけたものではない

これまでの記事では「計測で見えたボトルネックを順に潰すのは速い」と書いてきました。今回の最初の一手は、それとは違います。

Claude Code は素の状態で1回ベンチを回したあと、インデックスを足すところから始めずに、**データの持ち方を一度に書き換えました。** 理由は作業記録にこう残っています。

> この問題は構造が既知なので、個別に index を足す前にデータの持ち方を変えた

ISUCON12 予選は有名な問題で、何が重いか（SQLite にインデックスが無い、ファイルロックで排他している、閲覧履歴が300万行ある、ID 採番が MySQL、アプリが docker の中で `go run` されている）は広く知られています。Claude Code はそれを最初から知っていて、次のものを1コミットで入れました。

- テナントのデータ（参加者・大会・スコア）をプロセスのメモリに持ち、読み取りは全部メモリから返す。SQLite は永続化のためだけに書く
- ファイルロックをやめて、テナントごとのロックに
- 請求額は大会が終了した時点で確定させて保存する。初期データの分は、変換ツールが MySQL の閲覧履歴300万行から畳み込む（初期データは 270MB → 20MB）
- ID 採番をプロセス内に。docker をやめて、バイナリを直接起動

結果は 2,033 → 256,633 でした。効いてはいます。ただ、これは「計測して、見つけて、直した」のではなく「知っていたものを入れた」です。自分で作った CLAUDE.md の「1改善 = 1コミット = 1ベンチ」も、ここでは守っていません。

初見の問題で同じことをすると、壊したときにどれが原因か分かりません。実際この一括書き換えの直後は SCORE 0 が2回続きました。原因はアプリではなくベンチマーカー側（開けるファイル数の上限 1024）でしたが、一度に多くを変えた直後だったので、まずアプリを疑うところから始めています。

## 26万点で止まった原因は、ベンチマーカーを動かすマシンだった

3台構成にしても 259,537。サーバー側の応答は 14ms から 2ms に縮んでいるのに、スコアは同じでした。Claude Code が見ていたのはベンチマーカーを動かしているマシンの CPU で、95% でした。

ここで質問が来ています（抜粋）。

> 現在 259k 点ですが、ベンチ機 (c5.large) の CPU が 95% で飽和しており、サーバー側をこれ以上速くしても点が動きません。ベンチ機のインスタンスタイプを上げてよいですか？

[ISUCON14 のとき](/blog/isucon14-with-claude-code/)は、Claude Code がベンチマーカーを黙って変えていて、私は事後報告の1行を読み流していました。それ以来「ベンチ機のインスタンスタイプの変更は事前に確認する」をルールに入れてあり、今回はそのとおりに止まっています。

ただ、質問が出てから変更が済むまでに約50分かかっています。私の最初の返事は「推奨設定は？」で、推奨（16 vCPU）と理由を聞いてから承認しました。Claude Code は質問の前に、返事を待たずにできること（ドキュメントの整備、再起動試験）を済ませていて、あとは待つだけの状態でした。確認を求めるルールは、返事が遅れるとそのまま待ち時間になります。

承認して 16 vCPU に変えると、今度はサーバーが詰まりました。同じコードで FAIL です。1号機の nginx だけで CPU 136%（2 vCPU で 200% が上限）、2号機と3号機は 17%。TLS の終端と HTTP/2 と中継を、入口の1台が全部引き受けていたためです。

## TLS を3台に分ける

ここから先は、過去3回には無かった種類の改善でした。

**nginx を L4 の中継だけにして、TLS は3台の Go アプリが直接終端する。** テナントのデータは各台のメモリにあるので、同じテナントのリクエストは必ず同じ台に届く必要があります。そこで nginx は TLS の中身を見ずに、接続の最初に平文で送られてくるホスト名（SNI）だけを読み、そのハッシュで行き先を決めます。これで 828,537。

その先はプロファイルを見ながら進んでいます。

- **RSA 署名を OpenSSL に（+8%）。** ベンチマーカーは参加者ごとに新しい TLS 接続を張り、セッションの再開もしません。1回のベンチで約6万回のハンドシェイクがあり、そのたびに RSA-2048 の署名が1回走ります。Go 標準の実装で 1.37ms、OpenSSL を呼ぶと 0.60ms でした
- **HTTP/2 をやめる（+13%）。** ランキングの API だけ平均 3.7ms かかっていて、内訳を測ると、レスポンスを作るまでは 0.3ms、書き出しに 3.4ms でした。HTTP/1.1 にすると 0.24ms。ベンチマーカーは参加者1人につき1接続で、順番にリクエストを投げるので、多重化の利点がありませんでした

HTTP/2 については、[ISUCON13](/blog/isucon13-with-claude-code/) でも「切ったら安定した」、ISUCON14 では「入れたら nginx が軽くなった」と、毎回結果が違います。問題ごとに測るしかなさそうです。

## 証明書は差し替えなかった

RSA 署名は、OpenSSL にしてもなおアプリの CPU の3〜4割を占めていました。ここでまた質問が来ます（抜粋）。

> サーバー証明書を自前の ECDSA 自己署名証明書に差し替えればこのコストがほぼ消えますが、レギュレーション解釈が割れる変更です（練習用 AMI の証明書が元々自己署名でベンチが検証していないから通るだけで、本番では運営配布の証明書なので使えない手）。どうしますか？

推奨は「差し替えない」で、私もそれを選びました。スコアは上がったはずです。ただ、練習環境が緩いから通るだけの手を入れても、本番で使えるものは何も増えません。

ベンチマーカーの変更と違って、こちらは事前に決めたルールに名指しで書いてあったわけではありません。「レギュレーションの解釈が割れる変更は確認する」という一般的な項目に、Claude Code が自分で当てはめて聞いてきたものです。

## 100万点から先は、練習環境が詰まる

1号機を中継専任にすると、管理者向けの API が速くなり（平均 1.9ms → 0.56ms）、ベンチマーカーが作るテナントが 284 → 574 に増えて、1,197,784 が出ました。ところが同じ構成でもう一度測ると FAIL します。

負荷走行が終わる瞬間（開始からちょうど60秒）に、`dial tcp ... i/o timeout` というエラーが 0件の回と数十〜千件の回がある。エラーは1件につき 1% の減点で、100件を超えると FAIL です。

Claude Code はこれを1時間以上追いかけています。順番に書くと次のとおりです。

1. **サーバーが接続を取りこぼしているのでは** → 別の台から入口への接続時間を測り続けると、負荷中も 0.3ms 前後で一定。取りこぼしのカウンタも 0。違う
2. **1号機の TCP のメモリが足りていない** → これは実在しました。nginx が接続1本あたり約 50KB のバッファを持ち、3万接続で 1.5GB。カーネルが受信キューでパケットを捨てていた。直したが、エラーは消えない
3. **ベンチマーカー側のポートの再利用が早すぎる** → 一部はこれだった。設定を変えたら悪化したので戻した
4. **サーバー側から使われていない接続を切る** → FAIL。調べると、接続はほぼ全部が生きている参加者のもので、間引けるものが無かった
5. **残った説明**: ベンチマーカーから入口への同時接続が約 3.2万を超えると、ベンチマーカー側で新しい接続を張る処理が遅くなる。負荷が終わる瞬間に接続の途中だったものが、エラーとして数えられる

5 は状況証拠からの推定で、ベンチマーカーのマシンの上では測っていません。ただ、最高点の構成では同時接続が毎回 4.2〜4.4万あり、ベンチマーカーの CPU が 48% から 66% に上がっていました。同時接続が 3.3万で収まる構成では、6回測ってエラーは最大2件です。

厄介なのは、**サーバーを速くするほど悪化する**ことです。応答が速いと参加者が離脱せず、接続が増えます。RSA 署名を同時に1本だけに絞る変更は、参加者情報の API を平均 11.9ms から 0.32ms にして、減点前のスコアを 128万に上げました。そして 235件のエラーで FAIL しました。

最終的に、テナントを3台に均等に載せる構成に戻しています。1号機は nginx と CPU を取り合うので、そこに載ったテナントは遅くなります。この構成では同時接続が 3.3万で収まりました。速くできるのに、しないほうが点が安定する。

## 失敗したこと

51回のうち FAIL は10回、エラーで減点された回がそのほかに16回ありました。多くは前述のベンチマーカー側の事情ですが、Claude Code 自身の失敗もあります。

- **ビルドが失敗したまま、古いバイナリでベンチを回した。** パッチでファイルの後半を消してしまい、ビルドエラーが出ていたのに、出力を絞って表示していたせいで見落としました。スコアが前回とほぼ同じだったので「効果なし」と記録しかけています
- **デプロイで `main.go` が配られていなかった。** バイナリ名と同じ名前のディレクトリを、除外指定が巻き込んでいました
- **測る前に直して、外した。** ランキングが遅い原因を SQLite の書き込みだと考えて非同期にしましたが、変化なし。そこで初めて内訳を測り、遅いのは書き出しだと分かってから、TLS のレコード分割を疑ってまた外し、HTTP/2 にたどり着いています。そのあとスコア入稿の遅さにも同じ見立て（SQLite の書き込み）で手を入れて、これも外しました。測ってみると、時間のほとんどはリクエストボディの到着待ちでした

## 公式の解説と答え合わせ

終わってから、公式の [ISUCON12 予選問題の解説と講評](https://isucon.net/archives/56850281.html)を Claude Code に読ませて、今回の実装と突き合わせてもらいました。作業中には読ませていません。当日のマニュアルも AMI に入っておらず、レギュレーションは Claude Code の記憶をもとにしています。

| 公式の解説 | 今回 |
|---|---|
| 閲覧履歴は最初の1回だけあればよい（320万行 → 20万行） | ✅ さらに進めて、終了済みの大会は確定した請求額に畳んだ |
| スコアは参加者ごとに最後の1行だけ（370万行 → 18万行） | ✅ |
| ファイルロックをやめてトランザクションに | ✅ テナントごとのロックに |
| ID 採番を MySQL から UUID などに | ✅ プロセス内で採番 |
| 請求額は大会の終了時に1回だけ計算して保存 | ✅ |
| ランキングをキャッシュ（入稿後3秒の猶予がある） | ✅ 入稿時に JSON まで作っておく。猶予は使わず即時に反映 |
| N+1 の解消 | ✅ メモリから返すので無くなった |
| SQLite のままか、MySQL に移すか | SQLite のまま。ただし読み取りには使わない |
| SQLite のまま複数台: テナント単位で振り分け | ✅ nginx が SNI のハッシュで振り分け |
| **負荷が高すぎるときは 429 を返して調整できる** | ❌ 知らなかった |

解説にある改善は、最後の1つを除いて全部入っていました。最初の一括書き換えは、解説の「予選突破相当の 24,000点」のチューニング項目をほぼ含んでいて、それで 25万点です。想定されたルートを、1コミットでなぞった形でした。

複数台構成について、解説は運営側で検討した案として「Redis にテナントとホストの対応表を持ち、nginx の Lua で振り分ける」を挙げ、「取り扱いに慣れた人でないと時間内に実現することは難しいかもしれません」と書いています。今回の SNI ハッシュは対応表が要りません。新しいテナントの DB は、担当する台が最初のアクセスで作ります。課金処理が課題になるという指摘は、テナントごとの合計額だけ MySQL に置くことで解いていました。

外したのは 429 です。解説によると、テナントの追加と大会の開催の API は、429 と `Retry-After` を返せば、ベンチマーカーにその秒数だけ待ってから再試行させることができ、「負荷が高すぎる場合の調整弁として使用可能」とあります。

これは、今回の最後の1時間にそのまま関係しています。Claude Code は「参加者が増えすぎてベンチマーカーが詰まる」ところまで突き止めましたが、負荷のほうを抑える手は採っていません。429 が使えることを知らなかったからです。実際には、作問者が用意した正規の調整弁がありました。マニュアルを読めていれば、最高点の構成を安定させる手があったかもしれません。試してはいないので、効いたかどうかは分かりません。

### 現在地

[ISUCON14 の記事](/blog/isucon14-with-claude-code/)では、Claude Code は「計測で見えるものには強く、問いを立てる部分には人が介在する余地がある」と書きました。今回は少し違うものが見えています。

**知っている問題は、計測より先に知識で解く。** 最初の25万点はそうでした。速いのは確かです。ただ、ISUCON の本番は初見の問題なので、この速さは本番では出ません。有名な過去問で AI に練習を回させるときは、出てきた手のどこまでが「測って見つけたもの」なのかを分けて見る必要があります。

**止まるべきところで止まるようになった。** ベンチマーカーの変更と証明書の差し替えは、どちらも聞いてきました。前者は過去の失敗から足したルール、後者は「解釈が割れる変更は確認する」という一般的なルールから、Claude Code が自分で該当すると判断したものです。

**引き際の見立ては妥当だった。** 「これ以上の改善はいけそう？」と聞いたときの答えは、安定して通るスコアはあと数%、サーバー側の手は残っているが有効なスコアとしては回収できない、ここで終了を勧める、でした。

そして今回も、環境の TTL を2時間45分残して終わっています。3回続けて同じです。ただ今回は、止まった理由が「締めの作業が済んだから」ではなく「これ以上は練習環境の調整にしかならない」でした。
