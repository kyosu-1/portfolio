# Claude Code に ISUCON13 を回させたら 705,235点だった

> この記事の文章は、作業記録をもとにほとんどを AI（Claude Code）が書いています。

[private-isu](/blog/private-isu-with-claude-code/)、[ISUCON14](/blog/isucon14-with-claude-code/) に続いて3回目です。今回は **ISUCON13**（ISUPipe、ライブ配信サービス）を、環境構築から計測・改善・デプロイ・記録まで Claude Code に回させました。

最初のプロンプトは1つです。「isucon14-2026 や private-isu-2026 と同様に、isucon13 について isuenv で環境構築をして、継続・改善を回して高得点を狙いたい。改善は必ず記録するように。マニュアル・レギュレーションの確認もしつつ、CLAUDE.md や skill の整備も必要に応じてして。これから離席するので、環境構築を行なったあと改善を回し続けて高得点を狙ってください。本番相当で、3台構成、ベンチは分離してお願いします。このディレクトリをリポジトリとして git 管理して、最終的に private repository を立てて push しておいて」。前回のリポジトリを雛形として読ませる以外の準備はしていません。

そこから **1時間20分は放置**して、戻ってからは短い質問と指示を10回ほど挟んでいます。コードは1行も書いていません。モデルは今回は **Claude Fable 5.1** です。

- リポジトリ: [kyosu-1/isucon13-2026](https://github.com/kyosu-1/isucon13-2026)
- 環境構築に使った自作CLI: [kyosu-1/isuenv](https://github.com/kyosu-1/isuenv)

### 本番との環境の違い

ISUCON13 本番の優勝スコアは [468,006点](https://isucon.net/archives/57993937.html)（NaruseJun）でした。今回の環境は次のとおりで、競技サーバーとベンチマーカーのスペックは本番と同じです。

| | 本番 | 今回 |
|---|---|---|
| 競技サーバー | c5.large × 3 | c5.large × 3（公開 AMI `isucon13-20231128102223`） |
| ベンチマーカー | 運営の ECS（8 vCPU / 8 GB） | 同じ VPC の c5.2xlarge（8 vCPU）。プロセスを cgroup で 8 GB に制限 |
| ドメイン | `*.u.isucon.dev` | `*.u.isucon.local`（AMI 側の置き換え） |
| 時間 | 8時間 | 環境構築から最終計測まで 3時間40分 |

ベンチマーカーのメモリ制限は、戻ってから「本番のベンチは ECS の 8 vCPU / 8 GB なので合わせて」と伝えて入れたものです（ピーク RSS は 525 MB だったので結果は変わりませんでした）。前回はベンチマーカーを途中で勝手に変えていたので、今回は CLAUDE.md のルールどおり、インスタンスタイプは最初から最後まで同じです。

本番でさくらインターネット賞の対象になった「名前解決成功数」は最多で 188,517 でした。今回の最終構成は1回あたり約 179,000 です。

## ISUPipe は DNS が絡む

ISUPipe のスコアは、視聴者がライブ配信に投稿した投げ銭の合計です。配信者ごとに `<名前>.u.isucon.dev` のサブドメインがあり、ベンチマーカーはそれを競技サーバーの DNS で名前解決してからアクセスします。さらに **DNS 水責め攻撃**（ランダムなサブドメインを大量に問い合わせる）が走行中に来ます。

初期実装の DNS は PowerDNS で、バックエンドが MySQL、キャッシュは全部無効でした。攻撃の問い合わせは全部 NXDOMAIN なのに、1回ごとに MySQL を2〜3回引きます。MySQL を分離した直後の計測で、DNS 由来のクエリが **DB 時間の 36%**、PowerDNS の CPU が 29%、全問い合わせをログに書く journald が 4%。ユーザー登録も `pdnsutil add-record` をプロセス起動していて1回 150ms かかっていました。

Claude Code は PowerDNS のチューニング（インデックス、ログ停止、キャッシュ）を検討したうえで、**PowerDNS を止めてアプリの中に DNS サーバーを持つ**ことを選びました。理由を聞くと、次の説明でした。

- キャッシュを有効にしても、水責めはランダムな名前なので当たらない。負のキャッシュを入れると、問い合わせ直後に登録されたユーザーの反映（2秒以内）と衝突しうる
- 正しい答えの源泉は users テーブルとゾーンファイルに尽きる。アプリはすでにユーザーをメモリに持っているので、DNS のために別の状態を持つ必要がない
- マニュアルが要求しているのは「53/UDP で A レコードを返す」「結果は3台の IP」だけで、ミドルウェアの入れ替えは明示的に許されている

置き換えは miekg/dns で150行ほどです。登録されていない名前は即 NXDOMAIN を返し、登録は DB コミット後にメモリに反映するので「登録が返った時点で引ける」が保証されます。この置き換え自体はスコアを 3% しか動かしませんでしたが、名前解決成功数が 2.7万 → 17.9万回/分になり、失敗は0になり、DB とアプリの CPU が空きました。その空きが直後の「nginx 分離 +68%」の余地になっています。

1回目は FAIL でした。ユーザー名に大文字が含まれるのに（`wkGQKEWut2`）、DNS は大文字小文字を区別しないので小文字で引いて外しました。`pdnsutil` は黙って小文字で登録していたので、置き換えるとその隠れた仕様を自分で背負うことになります。

## 放置した1時間20分で120倍

戻ってきた 18:28 の時点で 385,724 でした。放置中に Claude Code がやったことは、計測で見えるものを順に潰す作業です。インデックス、`interpolateParams`、N+1 のメモリキャッシュ、DB と nginx の分離、DNS の置き換え。ISUCON14 のときと同じで、ここは速い。

途中で2つ、バグを踏んでいます。1つは、追加したインデックスのせいで `DELETE` + `INSERT` がギャップロックでデッドロックし、アイコン投稿に 500 が24件出たこと（UNIQUE にして upsert に直した）。もう1つは、モデレーション（NG ワードでコメントを消す処理）を1件ずつの DELETE から一括に直したら速くなりすぎて、消えたコメントの報告一覧が 500 を返すようになったこと。元実装でも起きるバグで、遅すぎて顕在化していなかっただけでした。どちらも1回のベンチで気づいて、次のベンチまでに直しています。

## 戻ってからの質問と、ベンチマーカー側の頭打ち

戻ってからの介入は、時系列でこれだけです。

- 「現在の得点は？（質問だからそのまま作業は続けて）」
- 「現在はどう？ボトルネックはどこになってる？」
- 「本番のベンチは ECS の 8 vCPU / 8 GB なので合わせてほしい」
- 「今後の改善方針は？」→「ok. 対応を進めて」
- 「他の改善は？現在のボトルネックは何？」
- 「最終形としようか」

改善の中身は指示していません。ただ「ボトルネックは？」と聞いた 18:52 の時点で、Claude Code の答えは「どのノードも CPU が飽和していない」でした。ベンチマーカーの出力を5秒刻みで数えると、負荷開始から10秒で配信の予約枠（初期データで1時間5枠）が人気の時間帯で埋まり、以後は予約が全部 400 になって、視聴者の投入レートが 200/5秒 → 150/5秒 に落ちる。これはリファレンス実装でも同じ挙動で、**負荷の上限はベンチマーカー側で決まっています。** スコアは「完了した視聴者数 × 約195」でほぼ一定でした。

それでも、そこから 42万 → 70万まで伸びました。効いたのは JSON エンコーダの差し替え（+17%）、コメントとリアクションのメモリ化、そして nginx を3台に分散すること（+24%）です。最後のは、アプリ内 DNS の A レコードを名前ごとに変えて、TLS 終端を3台で分担させています。ここで分かったのは、**ベンチマーカーは名前解決どおりには来ない**こと。接続を使い回すので、nginx の access log で実測しないと分散の割合は決まりませんでした。

最終構成では競技サーバー3台が 60〜70%、ベンチマーカーが負荷の後半に 75% です。ベンチマーカーは本番相当のスペックなので、これは「本番でも同じ壁」ということになります。

| ノード | 役割 |
|---|---|
| isucon13-1 | Go アプリ（状態をメモリに持つので1プロセス）+ アプリ内 DNS + nginx |
| isucon13-2 | MySQL + nginx |
| isucon13-3 | nginx（`pipe.u.isucon.dev` 宛。全リクエストの7割） |

## また自分から止まった

20:05 に、Claude Code は再起動試験を通して「一区切り」の報告を出していました。環境の TTL は9時間残っていました。前回の ISUCON14 でも同じことがあり、CLAUDE.md の「終盤は守りに入る」に沿って締めています。時間いっぱい回させたいなら、終わりの時刻を指示しておく必要がある。これは2回続けて同じ結論です。

ただ、そこで「今後の改善方針は？」と聞いたら、方針を3つ挙げて「1から着手します」と返してきたので、「ok. 対応を進めて」と言って続けさせました。その30分でスコアは伸びませんでしたが、**スコアが2つに分かれる原因**にたどり着いています。

## 64万と70万に分かれる原因を追いかけた

途中まで、同じコードで計測しても、スコアが 64万台の回と 70万台の回にはっきり分かれていました。普通のブレなら ±3% ほどで平均の周りに散るので、乱数ではなく何か原因があると考えました。最初に見つけた手がかりは「MySQL を再起動した直後の回が速い」で、Claude Code はそこから ANALYZE TABLE や再起動の組み合わせで6回ベンチを使い、**再現しなかった**ので「ベンチ側の乱数」と結論づけていました。

「方針は？」のあとに改めて、速い回と遅い回のログを5秒刻みで並べ直しました。遅い回は負荷開始30秒以降に視聴者・予約・アイコン変更が一斉に3割減り、そのとき pipe 宛の nginx の CPU だけが上がっている。リクエストあたりの nginx の仕事が増えている、つまり TLS ハンドシェイクを疑って、access log に接続 ID と TLS 再開の有無を出したところ、**新規接続 1,000〜2,000/5秒がすべてフルハンドシェイク**（ベンチマーカーはセッション再開を使わない）と分かりました。HTTP/2 は登録とログインだけが使っていて、切っても接続の数は変わらなかったのですが、**切った後は6回連続で 70万台**になり、遅い回は出なくなりました。因果の証明まではしていません。

## 失敗したこと

67回のうち FAIL は1回（前述の DNS の大文字）で、他は全部 pass です。revert した実験と、記録に残った失敗はこのあたりです。

- **pipe 宛の名前解決を MySQL のノードに向けた。** 全リクエストの7割が来るので DB が遅くなって −26%。「pipe は app / DB の無いノードへ」
- **nginx の `worker_connections` を上げただけ**で `worker_rlimit_nofile` を上げず、`accept4() failed (24: Too many open files)` で 5xx が57件
- **nginx の設定変更が黙って反映されていなかった。** `proxy_cache_path` の親ディレクトリが無くて `nginx -t` が落ち、デプロイスクリプトは旧設定のまま動いていた。`X-Cache-Status` ヘッダを出して確認して初めて気づき、デプロイが `nginx -t` の失敗で止まるように直した
- **スパム判定を配信者単位にする実験。** ベンチマーカーの「モデレート済みスパムの投稿が 201 で通った」というエラーが毎回130〜250件出るので試したが、減らず −7%。マニュアルに「ベンチ側の問題、減点対象外」と明記されている種類のエラーで、触るべきではなかった
- **MySQL 再起動が効くという仮説に6ベンチ使った**（前述）

## 公式の解説と答え合わせ

終わってから、公式の [ISUCON13 問題の解説と講評](https://isucon.net/archives/58001272.html) と突き合わせました。作業中には読ませていません。

| 公式の解説 | 今回 |
|---|---|
| インデックスの追加（初期 約3,000点 → 約10,000点） | ✅ 最初の改善で 7,288点。接続設定を足して 11,202点 |
| アイコンのハッシュを毎回計算しない（トリガーで事前計算） | ✅ メモリに持つ。`If-None-Match` の 304 も実装し、最後は nginx のキャッシュで返す |
| `fillXxxResponse` の N+1 を JOIN やキャッシュで消す | ✅ ユーザー・タグ・配信・コメント・リアクションを全部メモリに |
| 統計とモデレーションの事前計算 | ✅ ランキングのスコアをメモリで数え、モデレーションは1文の DELETE に |
| DNS: TTL を伸ばす | ✅ 120秒 |
| DNS: PowerDNS のキャッシュを有効にする | ➖ PowerDNS ごと置き換えた |
| DNS: バックエンドの DB にインデックス | ✅ 最初に入れた（置き換え後は不要） |
| DNS: DNS の DB をアプリの DB と分ける | ➖ DB を使わない |
| DNS: dnsdist で NXDOMAIN をレート制限 | ❌ 不要だった。NXDOMAIN がメモリ参照1回で返る |
| DNS: ワイルドカードで登録時のレコード追加を無くす | ➖ 同じ効果（登録時の `pdnsutil` を廃止） |
| 3台構成: nginx / DNS / DNS の DB → アプリ → アプリの DB | 🔀 アプリ + DNS + nginx / MySQL + nginx / nginx |

解説の想定は、DNS を「PowerDNS を残したまま軽くする」方向です。今回はそれを見ずに「無くす」方向に行きました。解説にはベンチマーカーが水責めをレート制限していることも書かれていて、たしかにベンチマーカーの出力では並列数が2秒ごとに上がって15で止まっています。その上限まで上げられても応答が落ちなかったので、名前解決失敗は0でした。

3台構成も解説と違います。解説は nginx と DNS を同じノードに置き、アプリと DB をそれぞれ独立させる形です。今回はアプリの状態がメモリにあるので1プロセスから動かせず、代わりに nginx の TLS 終端を3台に散らしました。どちらが良いかは、どこが最初に飽和するかで決まります。今回はアプリではなく TLS でした。

### 現在地

前回は「計測で見えるものには強く、文章に書いてあるヒントを自分から戦略に変えるところに人が介在する余地がある」と書きました。今回、人の介入で動いたのは次の2つです。

- ベンチマーカーのスペックを本番に合わせる（公平性。スコアには影響しなかった）
- 「今後の改善方針は？」から始まった、スコアが2つに分かれる原因の追跡（スコアではなく安定性）

スコアそのものは、放置と「作業は続けて」の間にほぼ全部出ています。前回との違いは、今回は問題の構造（予約枠で負荷の上限が決まる、ベンチマーカーは名前解決どおりに来ない、全接続がフルハンドシェイク）を Claude Code が自分で計測から掘り当てていることです。ただし、掘るきっかけになったのは「ボトルネックは？」「方針は？」という、中身のない質問でした。質問の中身が要らなくなった一方で、質問すること自体はまだ要る。それが今回の現在地です。
