# Claude Code に ISUCON11 予選を回させたら 7,186,580点だった

> この記事の文章は、作業記録をもとにほとんどを AI（Claude Code）が書いています。

[private-isu](/blog/private-isu-with-claude-code/)、[ISUCON14](/blog/isucon14-with-claude-code/)、[ISUCON13](/blog/isucon13-with-claude-code/) に続いて4回目です。今回は **ISUCON11 予選**（ISUCONDITION、椅子のコンディションを記録・閲覧するサービス）を、環境構築から計測・改善・デプロイ・記録まで Claude Code に回させました。

これまでと違うのは準備です。過去3回で得た知見を isucon-tools というリポジトリ（非公開）にまとめてあり、今回はそれを参照させました。最初のプロンプトは「isucon-tools の構成を参考にしつつ、isucon11予選を解いていきたい。環境構築は isuenv で。改善作業を回し、最高点を目指してください。TTL は6時間で設定して、回していきましょう」の1つです。

途中で口を挟んだのは5回ほどで、改善の中身は指示していません。**スコアが伸びたのは全部、私が何もしていない間です。** コードは1行も書いていません。モデルは **Claude Opus 5.5** です。

- リポジトリ: [kyosu-1/isucon11-qualify-2026](https://github.com/kyosu-1/isucon11-qualify-2026)
- 環境構築に使った自作CLI: [kyosu-1/isuenv](https://github.com/kyosu-1/isuenv)

### 本番のスコアとは比べられない

これは過去3回と同じ注意です。公開されているベンチマーカーを、競技サーバーと同じ VPC に置いた c4.xlarge で、1チームだけで回しています。本番のベンチマーカーがどう動いていたかは確認していません。後で書くとおり、このスコアは「負荷を出す側が詰まる」ことを前提にした調整の結果なので、なおさら本番の数字とは並べられません。

もう1つ、**このスコアは解釈が割れうる3つの設定に強く依存しています。** これも後で書きます。

## ベンチマーカーのスペックを最初に直した

最初に Claude Code が立てた環境は、ベンチマーカーが c5.2xlarge でした。「これは推奨環境？」と聞くと、公式の推奨ではなく、ISUCON14 の練習のときのメモ（「次は c5.2xlarge にする」）を流用しただけだという答えでした。

「推奨スペックで行きたい。その制約のもとでの最適化が必要なので」と伝えると、公式リポジトリの README に「競技者 VM は c5.large × 3、ベンチ VM は c4.xlarge」と明記されているのを見つけてきて、ベースラインを取る前に環境を作り直しました。

これは改善ではなく、測る前提を公式に揃えただけです。ただ、この問題はベンチマーカーの大きさで最適解そのものが変わるので、揃えずに始めていたら以降の話は違う形になっていたはずです。

## ISUCONDITION は「ユーザーが増える = 良い」ではなかった

ISUCONDITION のスコアは、ユーザーが椅子（ISU）のコンディションやグラフを見ることで入ります。実測では点の9割以上がグラフで、グラフの等級は「その日の各1時間に何件のコンディションがあるか」の最小値で決まります（21件以上で Good）。

ISU は仮想時間（現実の3万倍速）の1分ごとにコンディションを作り、10件ずつ送ってきます。定刻どおりなら1時間に30件届きます。

そして、閲覧者がトレンド（`GET /api/trend`）の変化を見るとユーザーが増えます。ユーザーが増えると ISU も増えます。

ここまでは「速くすれば負荷が増えて点も増える」という、ISUCON でよくある形に見えます。実際は逆でした。

| trend の更新間隔 | ユーザー / ISU | スコア |
|---|---|---:|
| 500ms | 102 / 534 | 435,409 |
| 1秒 | 37 / 201 | 987,450 |
| 2秒 | 17 / 91 | 2,070,376 |
| 4秒 | 11 / 66 | 3,306,678 |
| 60秒（増えない） | 7 / 48 | 4,566,522 |

**ユーザーを増やさないほど高い。** 初期の7人のまま回すのが最高でした。

### 気づくまで

41万点の時点で、サーバー3台の CPU は 53% / 54% / 18% と余っていました。コンディションの読み出しをメモリ化しても +5% しか伸びず、グラフの質（Good の比率）も変わりません。

そこで Claude Code は DB を集計しました。コンディションの書き込み時刻を5秒刻みで数えると、こうなっていました。

- 1つの ISU から届く件数は、開始から25秒までは1時間あたり30件。そのあと 26 → 14 → 8 件と落ちていく
- その間に ISU は 51台から518台に増えている
- 全体の受信は5秒あたり18.5万件で頭打ち

ISU が増えるほど、ベンチマーカーが全部の ISU を定刻に送れなくなっていました。1時間に8件しか届かなければ、グラフは全部 Worst です。ベンチマーカーの vmstat を見ると、開始直後から CPU が86〜95%で張り付いていました。

ここから問題が変わりました。サーバーを速くする問題ではなく、**ベンチマーカーの CPU を点になる仕事に使わせる**問題です。以降の改善は全部この方向です。

- **trend の応答を遅らせる。** 閲覧者は応答を受け取るとすぐ次を取りに来ます。21人で1分に15,325回叩いていたのが、500ms 遅らせると6,168回になり、+11%
- **HTTP/2 を切る。** +20%。ベンチマーカーは Go 製で、HTTP/2 のクライアントは HTTP/1.1 より重いようです
- **コンディションを1時間21件までしか保存しない。** Good の条件を超える9件は、ユーザーが読むページ数とグラフの JSON を増やすだけなので捨てる。+6%
- **gzip は逆効果。** 1回のログインごとに 743KB の JavaScript を取り直していたので圧縮してみたら −10%。ベンチマーカーが伸長で重くなりました

### 下がっても revert しなかった

表の 16:24 を見ると、trend をキャッシュして 18,000 → 9,150 に下がっています。CLAUDE.md には「スコアが下がったら revert」と書いてあります。

Claude Code は revert しませんでした。ベンチマーカーの出力から「ユーザーが増えました」が出始めたことを読み取り、タイムアウトが消えて負荷が増えただけで方向は正しい、と判断して次の手に進んでいます。次の2手（静的ファイルの nginx 配信とログ停止）で 17,561 に戻りました。

皮肉なのは、その約30分後に「ユーザーを増やさない方が高い」と分かって、trend を60秒間更新しない設定に落ち着いたことです。ただし最初の実装（リクエストのたびに全 ISU の全コンディションを読む N+1）のままでは1秒でタイムアウトするので、キャッシュ自体は必要でした。

## 解釈が割れうる3つの設定

710万点は、次の3つに依存しています。

| 設定 | 内容 | マニュアルの記述 |
|---|---|---|
| trend を60秒間更新しない | ユーザーが増えなくなる | コンディションの反映が遅れることは許容 |
| trend の応答を 900ms 遅らせる | 意図的な遅延 | 禁止の記載なし（タイムアウトは1秒） |
| コンディションを1時間21件まで | 超過分を保存しない | データ欠損は許容（初期実装は9割を捨てている） |

Claude Code は、どれもマニュアルの範囲内と読んで採用しつつ、途中経過を聞いたときに「解釈が割れうるので、最終形にするかはあなたの判断です」と自分から挙げてきました。3つとも環境変数で外せるようになっています。

私の感覚では、1つ目と3つ目は公式の解説（後述）が挙げている負荷調整と同じ種類のものです。2つ目の「わざと遅らせる」は、禁止されていないとはいえ、作問者が想定した解き方ではないと思います。

3つとも外した構成の最適点は測っていません。近い条件（trend 1秒・遅延なし・全件保存、HTTP/1.1 化とアプリの移動の前）では 987,450 でした。

## 本番ではベンチマーカーは見えない

終わってから、過去3回の知見をまとめている isucon-tools に今回の分を反映してもらおうとして、気づいたことがあります。**本番ではベンチマーカー側のメトリクスは見えません。** 「ベンチマーカーの CPU が86%」を根拠にした判断は、本番ではできないはずです。

これを Claude Code に言うと、振り返って整理してくれました。判断の決め手になった観測は、ほとんどサーバー側で取れていたそうです。

- サーバーを速くしても、エンドポイント別のリクエスト数が増えない（alp の COUNT が改善前後で同じ）
- 3台とも CPU に余裕があるのにスコアが伸びない
- 1つの ISU から届く件数が時間とともに減るのに、サーバー側の 4xx やタイムアウトはほとんど無い
- 1接続あたりの往復が 12.8ms で、そのうちサーバーの時間は 1ms 未満（nginx のログを接続ごとに束ねると分かる）

ベンチマーカーの vmstat は「答え合わせ」に使っただけでした。本番では、相手側の CPU なのか、シナリオが意図的に入れている待ちなのかは区別できません。ただ、区別できなくても打つ手は同じ（負荷は増やせない前提で、負荷量のつまみを振って測る）だというのが Claude Code の整理です。

isucon-tools には「ベンチ機の vmstat を必ず見る」としか書いていなかったので、「本番では見えない。サーバー側だけで切り分ける」という節を足しました。練習環境でしか取れない数字を根拠にする癖がつくと、本番で使えない知見が溜まっていきます。

## 環境

環境は自作の [isuenv](https://github.com/kyosu-1/isuenv) で作りました。

```sh
isuenv up isucon11-qualify --nodes 3 --bench-instance-type c4.xlarge --ttl 6h
```

最終的な役割分担は次のとおりです。

| ノード | 役割 | 負荷中の CPU |
|---|---|---|
| isucon11-qualify-1 | nginx（ユーザー向け。静的ファイルを直接返す） | 23% |
| isucon11-qualify-2 | MariaDB | 16% |
| isucon11-qualify-3 | nginx（ISU のコンディション受信）+ Go アプリ | 43% |
| ベンチマーカー | c4.xlarge | 86% |

ISUCONDITION は、ISU がコンディションを送る先のホスト名をアプリ側で決められます。それを3号機にすると、ISU からの POST だけが3号機に直接届きます。アプリは全コンディションをメモリに持つので1プロセスのままです。

サーバーが3台とも余っているのが、この問題の最終形でした。

## 進め方

進め方は過去3回と同じで、違いは isucon-tools を読ませたことだけです。Claude Code は isucon-tools の「開始30分」の手順に沿って、サーバーの調査、初期状態の取り込み、`make deploy` / `make bench` の道具立て、CLAUDE.md と skill の作成、ベースライン2回までを自分で進めました。

- **計測なき改善は禁止。** 変更前に必ず実測の根拠を示す
- **1改善 = 1コミット = 1ベンチ**
- **サーバー上で直接編集しない。** ローカルの git が正
- **ベンチマーカーのソースは読まない。** プロファイルも取らない。外から観測できるものだけで判断する

道具は前の問題のものをコピーするのではなく、isucon-tools の指針を読んでその場で書かせています。環境を立ててから最初のベースラインが出るまで約3分、インデックスの改善が入るまで約7分でした。

## 失敗したこと

- **deploy が失敗したままベンチを回した。** 最後の実験（アプリが直接 TLS を受ける）を戻すとき、アプリが443番を握ったまま nginx を起動しようとして失敗し、そのままベンチが走って 1,000点が記録されました。再 deploy で直り、記録には無効と注記しています
- **ソースの一部を消した。** 文字列の一括置換で、関数の間にあった変数定義ごと消していました。`go vet` で気づいて git から戻しています
- **アプリの起動を待たずに疎通確認した。** 起動時に全コンディションを読むようにしたら、ベンチ前の確認が先に走って中止になりました

「これ以上はベンチマーカーを変えずには上げられない？」と聞くと、残りはサーバー側で数%という見立てでした。「試しにやってみて」と頼んだ2つ（アプリが直接 TLS を受ける、TLS 1.2 に固定）は、下がるか変化なしで、どちらも戻しています。

## 公式の解説と答え合わせ

終わってから、公式の [ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)（2021年8月）を Claude Code に読ませて、突き合わせてもらいました。作業中には読ませていません。

| 公式の解説 | 今回 |
|---|---|
| `isu_condition` に `(jia_isu_uuid, timestamp)` のインデックス。複合主キーにするとさらに良い | ✅ 最初の改善。その後、主キーに |
| `POST /api/condition` を bulk insert に。キューに溜めて一定間隔でまとめて INSERT | ✅ 200ms ごとにまとめて INSERT |
| `GET /api/trend` に LIMIT 1 | ✅ その後、メモリから |
| `GET /api/condition` はレベルを列に持って LIMIT | ✅ 生成列で。その後、メモリから |
| グラフは24時間分だけ読む | ✅ その後、メモリから |
| アプリのログ出力を止める | ✅ |
| 複数台構成（DB 1台 + アプリ2台。POST を受けるサーバーを分ける） | △ POST の TLS 終端だけ別ノードに。アプリは1プロセス |
| `dropProbability` を下げる | ✅ 0 にして 108,374 → 228,052 |
| trend をキャッシュして定期的に更新 | ✅ |
| クライアントキャッシュ（304、`max-age`） | ✅ アイコンと静的ファイルに `max-age` |
| nginx を廃止して直接通信 | ❌ 試して下がった |
| unix ドメインソケット | ❌ 試していない |

解説は、Go 実装で「ここまでで15万点以上」「ここまでで65万点以上」と2段階の目安を挙げています。今回は trend をキャッシュして全件保存した時点が 228,052、3台構成で 415,536 でした。

面白いのは、解説が負荷の調整に触れていることです。trend の改善を入れると「ユーザと ISU が増えリクエスト数が急増します」とした上で、こう書かれています。

> 状況に応じて、trendの更新頻度を下げたり、dropProbabilityを上げたりすることで負荷を絞り、レスポンスタイムを速くすることも得点を稼ぐためには重要でした。

今回の「ユーザーを増やさない」「1時間21件に絞る」は、この調整を端まで振ったものです。作問者はつまみの存在を示していて、Claude Code は解説を読まずに同じつまみを見つけ、4点振って一番端が最高だと確かめました。

ただし、理由は少し違います。解説が言っているのは「負荷を絞ってレスポンスタイムを速くする」で、サーバーが詰まる前提です。今回はサーバーは余っていて、詰まっていたのはベンチマーカーでした。本番のベンチマーカーが同じように詰まっていたのかは分かりません。

### 現在地

過去3回は「計測で見えるものには強いが、問いを立てるのは人」という結論でした。ISUCON14 では、私が「分布とか分析した？」と聞くまで DB の集計をしていません。

今回は、聞く前に集計していました。読み出しをメモリ化してもスコアが動かなかった時点で、自分から DB を5秒刻みで数え、ベンチマーカーの飽和に辿り着いています。そこから「ユーザーを増やさない」方向を試すまで数分でした。

何が違ったのかは、はっきりとは言えません。モデルが違いますし、isucon-tools には過去の「アプリ機に idle が出ているのにスコアが伸びないなら、ベンチマーカーが先に飽和している」という知見が書いてあります。少なくとも、過去の練習で人が聞いて初めて出てきた問いが、今回は最初から手順の中にありました。

そして今回、人は点数に効いていません。ISUCON14 では、私が問いを立ててから伸びた分が約6%ありました。今回は0です。途中で聞いたのは進み具合と「これ以上は上げられない？」くらいで、そこから試した2つはどちらも伸びませんでした。解釈が割れる3つの設定も、私が判断を下す前に Claude Code が自分から挙げてきたものです。

私がやったのは、ベンチマーカーのスペックを公式に揃えさせたことと、終わってから「本番ではベンチマーカーは見えないよね」と言ったことだけです。前者は測る前提の話で、後者は次の練習のための話です。どちらも、この710万点の中身ではありません。
