# Claude Code に private-isu を回させたら211倍になった話と、そこで踏んだ計測の罠

ISUCON の練習として [private-isu](https://github.com/catatsuy/private-isu) を、**計測から改善・デプロイ・記録まで全部 Claude Code に回させたら**どこまで行くのかを試しました。

結果は **4,140 → 873,466（211倍）**、`fail = 0`、再起動試験も合格。

ただ、正直に言うと**スコアの伸ばし方より「計測の間違え方」のほうが収穫でした**。もっともらしい推論で最大の改善を捨てかけたり、プロファイラが指す一番大きい山を消しても速くならなかったり、そもそも計測器のほうが先に飽和していたり。この記事はそっちが本題です。

リポジトリ: [kyosu-1/private-isu-2026](https://github.com/kyosu-1/private-isu-2026)

## 環境と進め方

環境構築には自作の [isuenv](https://github.com/kyosu-1/isuenv) を使いました。ISUCON の過去問と private-isu の練習環境を、公開AMIから EC2 にコマンド一発で作って壊せる CLI です。

```sh
isuenv up private-isu --nodes 1 --bench --ttl 6h
```

private-isu のレギュレーションは **EC2 1台構成が前提**で、「起動したインスタンス以外の外部リソースを利用する行為（他のインスタンスに処理を委譲するなど）は禁止する」と明記されています。なので競技サーバーは `c7a.large`（2 vCPU / 3.7GB）1台のまま最後まで通しました。ベンチマーカーは競技対象外なので別インスタンスです。

進め方は最初にルールとして固定しました。

- **計測なき改善は禁止。** 変更前に必ず `measurements/` の根拠を示す
- **1改善 = 1コミット = 1ベンチ。** 混ぜない
- **スコアが下がったら即revert。** 粘らない
- **サーバー上で直接編集しない。** ローカルの git が正で、反映は `make deploy` だけ

`make bench` を叩くと、ログ初期化 → ウォームアップ → ベンチ → alp / pt-query-digest / vmstat / pidstat の収集 → `scores/log.md` への追記まで自動で走るようにしました。最終的に計測64回・コミット50件になりましたが、全部の改善に実測の根拠が残っています。

## 結果

ベースラインを取ってから最高記録までは **2時間32分**（21:57 → 00:29）でした。

| 時刻 | スコア | 変更 |

| 22:15 | 36,013 | `comments` / `posts` にインデックス追加 |

| 22:22 | 39,072 | テンプレートを起動時に1回だけparse |
| 22:29 | 50,489 | 画像をファイル化して nginx 直配信 |
| 22:33 | 75,586 | `makePosts` の N+1 を IN句でまとめる |
| 22:35 | 84,487 | `digest()` の fork/exec を廃止 |
| 22:38 | 169,403 | 一覧クエリを `STRAIGHT_JOIN` で駆動表固定 |
| 22:43 | 185,773 | MySQLチューニング |
| 22:45 | 193,350 | nginxチューニング |
| 22:54 | 204,414 | `SELECT *` をやめて BLOB を読まない |
| 22:57 | 212,264 | `interpolateParams` + コネクションプール |
| 22:59 | 218,768 | 新規投稿の画像をDBに保存しない |
| | | **← ここでベンチマーカーを `c7a.xlarge` に変更（アプリは無変更）** |
| 23:24 | 286,936 | 同一コードで測り直し。差の67,416点は計測器の性能 |
| 23:31 | 318,452 | `users` のインメモリキャッシュ |
| 23:37 | 332,972 | 投稿のINSERTと画像作成をトランザクションで囲む |
| 23:49 | 340,404 | `GOGC=400` |
| 23:53 | **758,615** | **画像に `Cache-Control` / `expires`** |
| 23:59 | 767,638 | ユーザーキャッシュに `account_name` 索引 |
| 00:03 | 803,871 | テンプレートのreflect呼び出しを事前計算に |
| 00:29 | **873,466** | 計測ログOFF + 再起動後 |

**「対直前の割合」で並べ替えていない**のは意図的です。同じ大きさの改善でも、そのときのスコアが低いほど割合は大きく出ます。インデックス追加は +714% ですが、これは適用時点が4,423点だったからで、絶対値では +31,590点。同じ手を後半に入れても同じ割合にはなりません。**割合は施策を順位付ける根拠になりません。**

その上で、桁が動いたのは次の4つでした。

- インデックス追加（4,140 → 36,013）
- 画像をファイル化して nginx 直配信（38,061 → 50,489）
- N+1 の解消と実行計画の固定（50,489 → 169,403）
- 画像にキャッシュヘッダ（340,404 → 758,615）

いずれも「1リクエストを速くする」ではなく **「やらなくていい仕事をやめる」** 系の変更です。private-isu を触ったことがある人には見慣れた顔ぶれだと思います。面白いのはここからです。

## 罠1: 観測を原因と取り違える

**これが一番の失敗でした。**

序盤にミドルウェアのチューニングを検討したとき、alp の出力がこうなっていました。

```
| COUNT  | METHOD | URI                             | ... | 2XX    | 3XX | 4XX | 5XX |
| 178220 | GET    | /image/[0-9]+(\.(jpg|png|gif))? | ... | 178220 |   0 |   0 |   0 |
```

画像の **3xx が 0件**。ここからこう推論しました。

> ベンチマーカーは条件付きリクエスト（`If-Modified-Since` / `If-None-Match`）を送ってきていない。だから `expires` を付けても 304 で軽くなる余地は無い。むしろクライアントがキャッシュして取りに来なくなると、リクエスト数が減ってスコアが下がる。よって入れない。

もっともらしいですが、**間違いです。**

**そもそもキャッシュヘッダを返していませんでした。** `Cache-Control` も `Expires` も無いレスポンスを受け取ったクライアントは、検証すべきキャッシュを持てません。だから条件付きリクエストを送りようがない。**3xx が0なのは相手の性質ではなく、自分の設定の帰結だった**わけです。

自分で作った状態を「相手はこういう仕様だ」と読んでいました。

後半、送信帯域が壁になっていることが分かった時点で（後述）、あらためて入れてみました。

```nginx
location /image/ {
  try_files $uri @app;

  expires 1h;
  add_header Cache-Control "public";
}
```

これだけです。画像のバイト列には一切触っていません（触ったら失格）。変えたのは配信時のヘッダだけ。

| | 前 | 後 |
|---|---:|---:|
| `/image/` のリクエスト数 | 178,220 | **514,236** |
| うち 304 | 0 | **505,165** |
| 60秒間の送出ボディ合計 | **52.7 GB** | **2.0 GB** |
| スコア | 340,404 | **758,615** |

リクエスト数は減るどころか **2.9倍に増えました**。1件あたりが軽くなった結果、同じ時間でより多く捌けるようになったためです。

> **「今その現象が出ていない」は「その現象が起きない」ことの証拠にならない。**
> 見送る前に自問する: **その観測結果は、自分の今の設定の帰結ではないか？**

同じ形の罠は他にもあります。「スロークエリが出ない＝クエリが速い」（`slow_query_log` が OFF なだけ）、「`wa` が 0%＝ディスクは余裕」（まだページキャッシュに載っているだけ）、「5xx が 0＝エラーなし」（アプリが 200 で空を返しているだけかもしれない）。

## 罠2: プロファイルの割合は、マシン全体の割合ではない

キャッシュヘッダで帯域の壁が外れたあと、アプリのCPUが idle 0% で飽和しました。pprof を取るとこうです。

```
text/template.(*state).evalCommand   38%(cum)
reflect.Value.call                   23%(cum)
```

しかも `reflect.Value.call` は **html/template のエスケープ関数自体が reflect 経由で呼ばれる**ことによるもので、テンプレートを使い続ける限り消えません。

なので `post.html` を手書きレンダラに置き換えました。レギュレーションで「レスポンス(HTML)のDOM構造」を変えたら失格なので、**出力バイト列の完全一致**を2段構えで担保しました。

- エスケープ表は推測せず、html/template に全ASCIIを通して実測して起こす（`\x00 " & ' + < >` の7つ。`=` は対象外で `+` は対象、というのは実測しないと分からない）
- 環境変数で「毎リクエスト両方レンダリングして突き合わせる」検証モードを付け、**753,122リクエスト分の実データで不一致0件**を確認

マイクロベンチでは狙い通りでした。

```
BenchmarkTemplate      197,701 ns/op   105,390 B/op   3,904 allocs/op
BenchmarkHandwritten    11,169 ns/op        24 B/op       1 allocs/op   <- 17.7倍
```

**それでもスコアは1ミリも動きませんでした。**

原因を掴めたのは、プロセス別CPUを測ってからです。ここで恥ずかしい話があって、それまで `top -bn1` を使っていたのですが、**あれは %CPU の差分が取れず全プロセス 0.0% になります**。ずっと無意味なデータを集めていました。`pidstat` に替えたらこうです（2 vCPU = 合計200%）。

| app | mysqld | nginx (worker×2) | memcached |
|---:|---:|---:|---:|
| 80.7% | 57.5% | 20.6% ×2 | 2.9% |

**アプリはマシン全体の約4割しか使っていない。** 数字を最後まで詰めるとこうなります。

- 実負荷で posts をレンダリングするのは約37,000ページ / 60秒
- 37,000 × 197µs = **7.3 CPU秒**
- 使えるCPUは 60秒 × 2 vCPU = **120 CPU秒**
- つまり全体の **約6%**。手書きにして浮くのはその大半 ≈ **5〜6%**
- **ノイズ幅 ±7% より小さい**

「効かなかった」のではなく **「単発の計測では判別できない大きさだった」**が正確です。

> **pprof の cum% が大きいことは「消せば大きく速くなる」を意味しない。**
> プロファイルは「アプリのCPU時間の内訳」を示すが、**アプリがマシン全体のCPUの何割か**は示さない。

同じ形で「クエリ本数を減らせば速い」も外しました。コメント取得の2クエリをウィンドウ関数1本に統合したところ、クエリ本数は半分になったのに **DB総実行時間が 62秒 → 84秒に増えました**。1本あたりが 0.4+0.3ms → 1.0ms になったためです。書き換えたら本数ではなく `pt-query-digest` の Response time の合計で比べる、という当たり前を踏み直しました。

## 罠3: 計測器のほうが先に飽和していた

中盤、アプリを最適化してもスコアが伸びなくなりました。アプリ機のCPUには余裕があるのに、です。

ベンチマーカー側の `vmstat` を取って分かりました。

| | us | sy | idle |
|---|---:|---:|---:|
| アプリ機 | 35% | 27% | **37%** |
| ベンチ機 | 78% | 18% | **1〜3%** |

**負荷をかける側が先に飽和していました。** private-isu の公式も競技サーバー `c7a.large` / ベンチマーカー `c7a.xlarge` を推奨しているのですが、isuenv が全ノード同一タイプだったので両方 `c7a.large` になっていたのが原因です。

isuenv に「ベンチ用ノードだけ別インスタンスタイプ」を足して（[PR #8](https://github.com/kyosu-1/isuenv/pull/8)）環境を作り直し、**同一コードで測り直したら 219,520 → 286,936**。差の67,416点はアプリの改善ではなく、まるごと計測器の性能でした。

それまで測っていたのはアプリの性能ではなかったということです。ボトルネックを探すときは、**測っている側が律速していないか**を先に潰す必要があります。

## レギュレーションは性能と同じ重みで扱う

private-isu のレギュレーションには「各サーバの設定およびデータ構造は任意のタイミングでのサーバ再起動に耐えること」とあります。これはスコアを何万点積んでも一撃で無効化されるので、改善の合間にも再起動試験を通していました。

そして**実際にバグを検出しました。**

```
failed to load users: dial tcp 127.0.0.1:3306: connect: connection refused
```

ユーザーキャッシュの初期ロードを `log.Fatal` にしていたため、再起動時に MySQL より先にアプリが起動したケースでプロセスが落ち、`Restart=` も指定していなかったのでそのまま復帰しませんでした。**本番なら「再起動＝スコア0」**です。

もうひとつ、「POSTしたデータが直後のGETに反映されていること」という採点条件でも引っかかりました。画像をファイル配信に切り替えたあと、`INSERT` をコミットしてからファイルを書いていたので、その隙間に別のリクエストが `GET /` で新着投稿を見つけて画像を取りに来て404、という事故です。アクセスログが決定的でした。

```
23:32:30 GET /image/14170.png status:404 apptime:0.031  <- アプリが404
23:32:30 GET /image/14170.png status:404 apptime:0.034  <- 2回目も404
23:32:30 GET /image/14170.png status:200 apptime:-      <- 以降はnginxがファイルで返す
```

トランザクションで囲んで、**投稿が見えるようになった時点で必ずファイルが存在する**ようにして解決しました。「POST直後に反映」は自分のレスポンスだけの話ではなく、**他のリクエストから見た可視性**の話でもある、というのがここでの学びです。

## 未解決: 連続でベンチを回すと壊れる

最後に正直な話を。**ベンチを間隔を空けずに回すと、2回目以降が必ず壊れます。**

| | スコア | fail |
|---|---:|---:|
| 1回目 | 869,580 | **0** |
| 直後の2回目 | 483,262 | **7,383** |
| 直後の3回目 | 468,992 | **7,616** |

失敗は `リクエストに失敗しました` という接続レベルのもの。潰した仮説は全部否定されました。

| 仮説 | 実測 | 判定 |
|---|---|---|
| ディスク枯渇 | ベンチ中ずっと1.8〜2.0GB空き | ✗ |
| EC2の帯域シェーピング | `bw_*_allowance_exceeded` がまったく増えない | ✗ |
| InnoDBのパージ遅延 | `History list length` = 0 | ✗ |
| アプリのリーク | goroutine 35 / RSS 49MB / MySQL接続 12 | ✗ |

追う過程で実問題は1つ見つかりました。**`GET /initialize` が DB は初期化するのに memcached を初期化していなかった**ことです。セッションが実行をまたいで積み上がり、64MBの上限に張り付いて eviction 72,396。しかも1ベンチだけで63.5MB使うので上限自体も足りていませんでした。**「初期化」の対象はDBだけではない**、というのは持ち帰りどころです。

ただこれを直しても連続実行の問題は再現しました。残っている仮説は**ベンチマーカー側のエフェメラルポート枯渇**（ベンチ終了数分後でも TIME_WAIT が 7,638 残る / 使えるポートは 28,231個）で、ここで時間切れです。おそらくアプリではなく計測環境側の問題です。

なお、この問題に気づくのが遅れたのは**`score` だけ見て `fail` を見落としていた**からでした。`success` が増えていても `fail` が数千あればスコアは半減します。当たり前ですが、やります。

## Claude Code に回させてみて

**並列化できるのは改善ループではなく、独立作業のほうでした。**

ターゲットもベンチマーカーも1台なので、ベンチは直列でしか回せません。並列にすると互いの計測を汚染します。一方で「ミドルウェア設定の調査」と「ドキュメント執筆」はアプリのコードに触らないので並列で回せて、これは実際に効きました。

失敗もあります。机上演習のつもりで出したサブエージェントが実サーバーを触り、**ベンチの最中に45秒かかるフルテーブルスキャンを流して計測を汚染しました**。並列で走らせるなら「サーバーの状態を変えない」を明示的な禁止事項として渡す必要があります。

あと、途中で `git revert` が失敗したあとに `--amend` を打って、**コミットが実態と違うラベルになる**取り違えも1件やらかしました。気づいた時点でメッセージを事実に合わせ直しましたが、自動で回す以上こういう事故は起きるものとして、履歴を後から検証できる状態にしておくのが大事だなと。

道具への投資は、そのまま**取れる選択肢の広さ**になりました。

- `make setup` で環境をゼロから3分で完全復元できるようにした → **環境を作り直す**という判断が取れた
- `make html-save` / `html-check` で出力HTMLの完全一致を確認できるようにした → **DOM不一致で失格になりうるレンダラ書き換えに踏み込めた**

やったことは全部 `docs/playbook/` と、Claude Code の skill (`.claude/skills/tuning-isucon/`) に落としてあります。skill は**スキルを渡さないサブエージェントに同じ問題を解かせてベースラインを取り、そこで再現した判断ミスを潰す形**で書きました。スキル無しの回答は `innodb_flush_log_at_trx_commit = 0`（プロセス再起動でデータを失うのでレギュレーション的にアウト）を提案したり、JOINをEXPLAINせずに投入したりと、今回まさに自分が痛い目を見たところを綺麗になぞってくれたので、そのまま教材になりました。

## おわりに

211倍という数字より、**「効かなかった記録」と「間違え方の記録」が資産になった**回でした。効いた手はどれも定石で、調べれば出てきます。でも「pprofで38%を占めていても消して速くなるとは限らない」「3xxが0なのは相手の仕様ではなく自分の設定の帰結かもしれない」は、実際に自分で外してみないと身につかない類のものだと思います。

環境は落としてあります。`make setup` で3分で戻せるので、続きは連続実行問題の決着からやります。
