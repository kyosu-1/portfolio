# Claude Code に private-isu を3時間回させたら 873,466点だった

ISUCON の練習に [private-isu](https://github.com/catatsuy/private-isu) を使って、**計測から改善・デプロイ・記録まで全部 Claude Code に回させたらどこまで行くのか**を試しました。

**事前準備はしていません。** private-isu のアプリコードもレギュレーションも当日その場で読ませています（レギュレーションはAMIに同梱されていないので、上流から取ってこさせるところから）。事前に用意してあったのは、環境構築用の自作CLI だけです。

**プロンプトもほとんど打っていません。** 最初に方針だけ書いたものを1つ投げて、あとは短い質問と方向修正が20回ほど。「isuenvのCLIを使って」「言語はGoで」「ベンチマーカーは編集も読解もしない」くらいで、改善そのものの指示は出していません。**コードは1行も書いていません。**

モデルは **Claude Opus 5**。skill やカスタムコマンドの類も事前には用意していません。

- リポジトリ: [kyosu-1/private-isu-2026](https://github.com/kyosu-1/private-isu-2026)
- 環境構築に使った自作CLI: [kyosu-1/isuenv](https://github.com/kyosu-1/isuenv)

## 環境

環境構築には自作の [isuenv](https://github.com/kyosu-1/isuenv) を使いました。ISUCON の過去問（isucon9〜14）と private-isu の練習環境を、公開AMIから EC2 上にコマンド一発で作って壊せる CLI です。

```sh
brew install kyosu-1/tap/isuenv

isuenv up private-isu --nodes 1 --bench --ttl 6h   # 環境を作る
isuenv ssh private-isu                             # SSH
isuenv list                                        # 稼働中の環境・概算コスト・残りTTL
isuenv down private-isu                            # 破棄
```

`--ttl` で指定した時間が過ぎるとインスタンス側から自動で terminate されるので、**落とし忘れて課金が続く事故が起きません**。ssh config も自動生成されるため `ssh private-isu-1` がそのまま通りますし、グローバルIPが変わっても `isuenv ssh` を打ち直せばセキュリティグループごと貼り直されます。

`--bench` は今回追加したオプションです。private-isu の公式推奨は競技サーバー `c7a.large` / ベンチマーカー `c7a.xlarge` なのですが、それまで全ノード同じインスタンスタイプでしか作れませんでした。途中でベンチマーカー側が先に飽和していることに気づいて足したものです。

## 進め方

最初にルールとして固定したのはこれだけです。

- **計測なき改善は禁止。** 変更前に必ず実測の根拠を示す
- **1改善 = 1コミット = 1ベンチ。** 混ぜない
- **スコアが下がったら即revert。** 粘らない
- **サーバー上で直接編集しない。** ローカルの git が正で、反映は `make deploy` だけ

そのうえで `make bench` を叩くと、ログ初期化 → ウォームアップ → ベンチ → 各種計測データの収集 → スコアログへの追記まで自動で走るようにしてもらいました。あとは延々これを回してもらうだけです。

最終的に計測64回・コミット50件。全部の改善にコミットメッセージと `measurements/` の実測根拠が残っています。

### 計測環境も選定から任せた

最初のプロンプトに書いたのは「**計測ツールも最適なものを選定して自動改善できるようにして**」の一文だけで、**ツール名は一つも指定していません**。以下は全部 Claude Code が自分で選んで入れたもので、`make bench` 1回につき `measurements/<timestamp>/` に揃います。

| 取るもの | 使ったツール | 何が分かるか |
|---|---|---|
| アクセスログ集計 | alp（nginxをLTSV形式に変更） | エンドポイント別の合計時間・回数・P99。どこを潰すか決める |
| スロークエリ集計 | pt-query-digest（`long_query_time=0`） | クエリ別の合計時間、`Rows examine` と `Rows sent` の比、呼び出し回数 |
| 実行計画 | `EXPLAIN` / `EXPLAIN ANALYZE` | 駆動表の選択、filesort の有無、実際に読んだ行数 |
| アプリのCPU内訳 | pprof（`localhost:6060`） | Goのどの関数がCPUを使っているか |
| マシン全体のCPU/IO | vmstat（**アプリ機とベンチ機の両方**） | CPUバウンドかIOバウンドか、そして負荷生成側が飽和していないか |
| プロセス別CPU | pidstat | app / mysqld / nginx / memcached のどれが食っているか |
| 転送量 | `/proc/net/dev`、`ethtool -S` | 帯域が上限に当たっていないか |
| レスポンスHTMLの同一性 | `make html-save` / `html-check` | テンプレートを触ってもDOMが1バイトも変わっていないか（変えると失格） |

最初から全部あったわけではなく、行き詰まるたびに自分で足していきました。`top -bn1` は %CPU の差分が取れず全プロセスが 0.0% になると気づいて pidstat に置き換え、スコアが頭打ちになった時点で「負荷をかける側が先に飽和しているのでは」と疑ってベンチ機側の vmstat を足す、といった具合です。テンプレートに手を入れる直前には、DOMが変わっていないことを確認する `html-check` を自分で作ってから着手していました。

## おわりに

今回やったのは、**private-isu を事前準備なしで雑に回したらどうなるか**という試行でした。skill も何も用意せず、計測環境の整備からその場で全部やってもらった結果がこれです。

定石は指示しなくても計測から順に出てきました。ただし private-isu は有名な練習問題で解法記事も大量に公開されているので、**学習済みの知識をなぞっただけ**という可能性は割り引いて読む必要があります。

今後は実際の ISUCON の過去問も使いながら、エージェント前提での戦い方を研究していきます。
