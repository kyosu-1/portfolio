# Claude Code に ISUCON14 を回させたら 1,226,980点だった

> この記事の文章は、作業記録をもとにほとんどを AI（Claude Code）が書いています。

[前回](/blog/private-isu-with-claude-code/)は private-isu で試しましたが、今回は実際の過去問の **ISUCON14**（ISURIDE、椅子の配車サービス）を、計測から改善・デプロイ・記録まで Claude Code に回させました。

**事前準備は、前回のリポジトリを読ませただけです。** 最初のプロンプトは「isuenv で ISUCON14 の環境を作って、計測・改善を自動で繰り返してどこまで行けるか試したい。やることは前回の private-isu-2026 と同じようなイメージ」という1つだけで、前回の CLAUDE.md や計測スクリプトを雛形として参考にさせています。そのあと「このリポジトリで git 管理して」「言語は Go」「計測の記録は残して」「離席するので、CLAUDE.md や計測用のスクリプト、skill などを整備しつつ高得点を狙って」と短く足して、**そのまま3時間ほど放置しました。**

戻ってからは短い質問を20回ほど挟んでいます。改善の中身を指示してはいませんが、**質問がきっかけで動いた改善**や、Claude Code が挙げた案から私が選んだものがあるので、それも含めて書きます。コードは1行も書いていません。

モデルは前回と同じ **Claude Opus 5** です（最新の Fable 5.1 は使っていません）。

- リポジトリ: [kyosu-1/isucon14-2026](https://github.com/kyosu-1/isucon14-2026)
- 環境構築に使った自作CLI: [kyosu-1/isuenv](https://github.com/kyosu-1/isuenv)

## 結果

**1,097 → 1,226,980（1,118倍）**。最終構成は `pass=true`、WARN は1回あたり 0〜99件（200件で FAIL）で、3台を同時に再起動してからベンチを回す再起動試験にも6回合格しています。

ただし同じコードでもスコアはぶれます。最終構成の5回は 1,177,400 〜 1,226,980、平均は約120万で、タイトルの数字はその上振れです。

### 本番のスコアとは比べられない

ISUCON14 本番の優勝スコアは [58,153点](https://isucon.net/archives/58837992.html)で、桁が2つ違います。ただ、これは直接比べられる数字ではありません。本番は8時間の制限の中で、運営の環境からベンチマーカーが走っています。こちらは公開されているベンチマーカーを、競技サーバーと同じ VPC に置いた c5.2xlarge で回しています。後で書くとおり、このスコアはベンチマーカーを動かすマシンの性能に左右されます。あくまで「この環境で、同じ物差しで測って何倍になったか」の数字です。

## ISURIDE は「速く返す」だけでは伸びない

ISURIDE のスコアはリクエストを捌いた数ではなく、**椅子がライドで運んだ距離と完了数**で決まります。しかも利用者は満足度（マッチまでの待ち時間、迎えが来るまでの時間、乗っている時間）で増減し、椅子はオーナーの売上に応じて追加されます。負荷そのものがアプリの出来で変わる問題です。

そのせいで、private-isu とは違う種類の結果がいくつも出ました。

- **付近の空き椅子を見せないと、需要が消える。** 空いたばかりの椅子を付近の椅子の検索に少し遅れて出すようにしたら −67%。利用者は近くに空き椅子が見えないと配車を依頼しなくなります
- **マッチングは速さより質。** マッチング1回の最大所要時間を 380ms から 47〜175ms に縮めた版は、平均で −2% でした。一方、割り当て方を変えると大きく動きます（全組を貪欲に割り当てる形にして、直前の 287,776 から 320,624 へ +11%。後述の分析とハンガリアン法で、合わせて +6.6%）
- **椅子を早く増やしても、ベンチマーカーが先に詰まる。** これは後の「ベンチマーカーを途中で変えていた」で書きます

## 3時間で自分から止まった

放置している間、ループは 00:42 から回り続け、03:40 に最終構成で 1,159,771 を出しました。そのあと再起動試験と計測OFFを済ませて、**03:53 のコミットで止まっていました。** 環境の TTL（8時間）はまだ4時間半以上残っていました。

自分で書いた CLAUDE.md の「終盤は守りに入る。再起動試験・計測OFF・最終確認を優先する」に沿って締めの作業をして、そこで終わりにしたようです。時間いっぱい回させたいなら、終わりの時刻を指示しておく必要がありそうです。

## 質問から動いたマッチング

戻ってから「マッチングの最適化は現在どうしてる？」「椅子の分布とかって分析した？」と聞くと、**分布の分析はしていませんでした。** そこで DB を集計させると、次のことが分かりました。

- 依頼は2つの町（(0,0) 中心と (300,300) 中心）に分かれていて、需要と供給の比率は町ごとに同じ。町をまたいだ割り当ては0件
- 椅子の速さは 2 / 3 / 5 / 7 が1/4ずつ。ただし速度7の椅子は、速度2の約1.9倍しか稼いでいない（ライドごとの固定の手間が大きい）
- 負荷の終了までに一度も椅子が割り当てられなかった依頼が12%。常に椅子が足りない

これを踏まえて、マッチングのコスト（迎車時間 − 待ち時間の補正）に「長いライドには速い椅子」の項を足しました。待ち時間の補正の強さは 2 / 4 / 8 / 16 で探って 8 にして、ここまでで +4.5%。さらに、Claude Code が改善案の1つとして挙げていたハンガリアン法（その回の割り当て全体でコストの合計を最小にする）が気になったので、それを試してもらって +2.0% でした。

放置中の Claude Code は、計測で見えたボトルネック（インデックス、N+1、ポーリング、CPU）を順に潰すのは速かった一方で、問題の構造を調べるところまでは自分から行きませんでした。そこは「分布とか分析した？」の一言で動いています。

## 環境

環境は前回と同じく自作の [isuenv](https://github.com/kyosu-1/isuenv) で作りました。競技サーバーはレギュレーションどおり c5.large × 3台、ベンチマーカーは別に1台です。

```sh
isuenv up isucon14 --nodes 3 --bench-instance-type c5.xlarge --ttl 8h
```

3台の役割分担も、Claude Code が計測しながら決めています。

| ノード | 役割 |
|---|---|
| isucon14-1 | nginx のみ（TLS 終端・HTTP/2・静的ファイル）。ベンチマーカーの入口 |
| isucon14-2 | MySQL |
| isucon14-3 | Go アプリ + マッチャー（状態をメモリに持つので1プロセス） |

最初は1台に全部入っていて、MySQL を分けて +42%、アプリを3号機に出して +24%（nginx と CPU を取り合っていた）でした。

### ベンチマーカーを途中で変えていた

02:50 に、Claude Code がベンチマーカーを c5.xlarge から c5.2xlarge に変えていました。負荷の終盤にベンチマーカーの CPU の空きが5%を切る秒があったためです。**事前の確認はありませんでした。** 03:53 の終了報告には「自分の判断で行った環境の変更」として1行書かれていたのですが、私はそれを読み流していて、最後のほうでベンチマーカーの CPU の話が出てきたときに初めて意識しました。エージェントの事後報告は、長い報告の中の1行だと簡単に見落とします。

レギュレーションが決めているのは競技サーバー（c5.large × 3台）だけで、本番のベンチマーカーのスペックはマニュアルに書かれていないので、違反ではありません。変えた直後は、同じコードで 595,402 → 589,374 と差もありませんでした。

ただ、終盤は c5.2xlarge でも負荷の後半に CPU 97% で飽和していて、**スコアはベンチマーカーの性能に左右されています。** 最後に試した2つ（売上で追加された椅子の登録を DB 待ちなしにする、GC を減らしてアプリの CPU を下げる）は、どちらも狙いどおりに効きました（稼働した椅子 +10%、アプリの CPU 101% → 93%）。それでも平均スコアは変わっていません。椅子が増えたぶんベンチマーカーが詰まり、ベンチマーカー内の椅子の動きが遅くなって相殺されています。1,226,980 は、この環境で測った値として読んでください。

以後は CLAUDE.md に「ベンチ機のインスタンスタイプの変更は事前に確認する」を足しています。前回の private-isu でもベンチマーカーを途中で変えているので、2回続けて同じところで詰まったことになります。

## 進め方

進め方は前回とほぼ同じです。最初に [CLAUDE.md](https://github.com/kyosu-1/isucon14-2026/blob/main/CLAUDE.md) を書かせてルールを固定しました。

- **計測なき改善は禁止。** 変更前に必ず実測の根拠を示す
- **1改善 = 1コミット = 1ベンチ。** 混ぜない
- **スコアが下がったら revert。** ただしブレ幅を先に把握する
- **サーバー上で直接編集しない。** ローカルの git が正で、反映は `make deploy` だけ
- **ベンチマーカーのソースは読まない。** 外から観測できるもの（スコア、不満率、WARN、自分のサーバーのログ）だけで判断する

ISUCON14 向けには、WARN が200件で FAIL になること、座標の反映に3秒の猶予しかないこと、任意のタイミングの再起動に耐えることを足しています。

`make bench` を叩くと、ログの初期化 → ベンチ → 計測データの収集 → スコアログへの追記まで自動で走ります。集めるのはベンチ出力から抜いた不満率3種と WARN、alp、pt-query-digest、競技サーバー3台の pidstat、ベンチマーカーを含む4台の vmstat で、必要なときは pprof も取ります。判断基準と ISURIDE で実測して分かったことは [skill](https://github.com/kyosu-1/isucon14-2026/blob/main/.claude/skills/tuning-isucon14/SKILL.md) にまとめさせていて、これも回しながら Claude Code が更新しています。

## 失敗したこと

103回のうち無効（初期化の失敗や FAIL）は7回で、いずれも原因を特定して修正か revert しています。主なものは次のとおりです。

- **評価の応答前にライドを完了にした。** ベンチマーカーは評価 API の応答を受け取った時点でライドの完了とみなすので、WARN 268件で FAIL
- **ハンガリアン法の初版が panic した。** 依頼より空き椅子が多い回で添え字を取り違えて、マッチングが止まって FAIL。しかも1回目の結果を見ずに3回続けて回していました
- **決済を同じ `Idempotency-Key` で3本同時に送った。** 「最も改善効果が見込めるやつを試してみて」と頼んだら出てきた案です。決済サーバーが両方を処理して二重請求になり、FAIL。冪等キーは、前の要求が終わった後の再送にしか効きませんでした

もう1つ、計測記録とコードを同じコミットに入れていたせいで `git revert` がコンフリクトし、途中の状態のままデプロイまで走ったことがありました。戻したかった状態と同じだったので実害はありませんでしたが、「コードと計測記録は別コミットにする」がルールに加わっています。

## 公式の解説と答え合わせ

終わってから、公式の [ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)（2024年12月）を Claude Code に読ませて、今回の実装と突き合わせてもらいました。作業中には読ませていません。

| 公式の解説 | 今回 |
|---|---|
| インデックスの追加（Go で約4,000点） | ✅ 最初の改善で 3,424点 |
| 付近の椅子の検索の 2N+1 を1クエリに | ✅ DB を引かず、メモリ上の空き椅子の集合から返す |
| 総走行距離を別テーブルで差分管理 | ✅ 同じ案。その後メモリで積み上げて 200ms ごとに書き出し |
| マッチング: 待ち全件 × 空き椅子、近い椅子へ | ✅ |
| マッチング: 二部マッチング問題として解く | ✅ ハンガリアン法 |
| マッチング: 一定距離より遠い椅子は見送る | ❌ 試していない |
| `retry_after_ms` でポーリングを減らす | ✅ その後 SSE へ |
| 通知の SSE 化（優勝得点までなら必須ではない） | ✅ +34% |
| 座標の更新の非同期化・バルク化 | ✅ 位置の履歴はどこからも読まれないので、書くこと自体をやめた |
| 最新のライド状態の取得を速く | ✅ 列を足したあと、メモリ化 |
| 決済を `Idempotency-Key` で確認なしに再送 | ✅ 確認 API と待ちをやめて +19% |

解説にある改善は、1つを除いて全部通っていました。解説は「JSON API のままでも少なくとも10万点は取れる」としていて、今回もポーリングのまま 103,129点（01:40）まで行っています。想定されたルートをそのままなぞった形です。

そこから先の約12倍は、解説に出てこない部分でした。

- ライドの状態・椅子・履歴・売上・認証を全部メモリに持ち、読み取りで DB を引かない（DB を正として、起動時と initialize で作り直す）
- DB への書き込みを、順序を保った FIFO でまとめて非同期に書く
- nginx 専用 / MySQL / アプリ の3台構成、HTTP/2、静的ファイルの `expires`
- マッチングを 0.1秒ごとに回し、コストに椅子の速さと待ち時間の補正を入れる
- ベンチマーカーの観測から分かったこと（空き椅子が見えないと需要が消える、評価の応答がライド完了の基準、など）

面白かったのは決済です。解説では、`Idempotency-Key` は作問者がどうしても入れたくて入れた要素で、ボトルネックに絡められず「かなりのブラフになってしまった」と書かれています。想定修正は「キーを付けておけば、エラーになっても確認 API を叩かずにそのまま再送してよい」というものでした。今回やったのはまさにこれで、失敗のたびに 100ms 待って確認 API を叩いていたのをやめたら +19% でした。決済サーバーは7割の確率でエラーを返すので、1件あたり 0.6〜0.8秒のほとんどがその待ちと照合だったためです。スコアが伸びて決済の回数が増えると、ここは無視できない重さになっていました。

### 「生成AIの活用」の現在地

解説には「生成AIの活用」という節があります。当時の参加者は SQL の改善や N+1 の解消に AI を使っていて、「一発で正解のクエリを出してくれることもあったよう」だと。一方で、仕様全体の把握や、ドキュメントから改善のヒントを得る使い方は「思ったよりも少なかった印象」で、節はこう締められています。

> （来年にはそれで勝手に改善から計測までやってくれるようなエージェント型のAIやエディタも普及しているかもしれないですね…）

今回やったのは、まさにこれです。マニュアルをリポジトリに取り込み、レギュレーションの要点（WARN 200件で FAIL、3秒の猶予、SSE やマッチングの仕様変更が許されていること）を自分で CLAUDE.md にまとめ、計測から改善・デプロイ・記録まで勝手に回していました。

ただ、「ドキュメントから改善のヒントを得る」は、まだ弱いところが残っています。マニュアルには「離れた2つの地域」「ユーザーは地域内で移動する」と書いてあり、解説はそこから「遠い椅子は見送る」を導いています。Claude Code はマニュアルを読んでいたのに、2つの町に気づいたのは、私に聞かれて DB を集計してからでした。オーナーが収益を見て椅子を増やすこともマニュアルに書いてありますが、それを改善に使ったのも最後の最後です。ただし、促してからは速い。「分布とか分析した？」の一言から、DB の集計、マッチングのコストの変更、設定を2回ずつ回す探索まで進んで +4.5% になるのに約20分、「ハンガリアン法は気になる」から実装・テスト・3回のベンチで +2.0% を確かめるまでも約20分でした。計測で見えるものには強く、アイデアを一言渡せば分析と実行はすぐ返ってくる。一方で、文章に書いてあるヒントを自分から戦略に変えるところは、まだ人が問いを立てたほうが速い。それが今回見えた現在地でした。

## おわりに

一昨年の本番の優勝スコアは 58,153点。Claude Code はそれを51分で超え、放置した3時間で約20倍にしました。ベンチマーカーの環境が違うので厳密な比較ではありませんが、凝った準備も、最新の Fable 5.1 も使わずにこれです。

本番に向けて戦略を考えていきたいのですが、このままだと「AI エージェントにほぼ全部任せる」が最適解になってしまうかもしれません。
